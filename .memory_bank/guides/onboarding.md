# Запуск новой страховой / новой клиники (плейбук масштабирования, D33)

Цель: добавление страховой или клиники — воспроизводимая процедура, а не разовая магия.
Принцип: **всё в БД-реестрах (фронт+бэк едины), никаких «левых списков на фронте»**.

## A. Новая СТРАХОВАЯ (письма с неизвестного домена)

1. **Домен → страховая.** Письмо с неизвестного домена остаётся без страховой → на `/insurers`
   завести СК (кнопка добавления) или добавить домен существующей (редактор доменов).
   Реестр один — таблица `insurance_company` (name/aliases/domains) — БД, сид merge, UI.
2. **Реестр правил на сайте СК.** Найти страницу-реестр (искать С СЕРВЕРА — российский IP,
   из-за рубежа сайты страховых блокируются: `python3 /opt/sib-intake/rules_registry.py <url>`).
   Занести в настройки СК: `rules.registryUrl` + `rules.registryKeyword`. Если СК правила
   не публикует (Совкомбанк/ВСК/Лучи) или страница JS/403 — `rules.registryNote` с причиной.
   Дальше **registry-watch следит сам** (еженедельно, в цепочке `sib-programs.service`):
   новые ДМС-редакции НОВЕЕ нашей — скачиваются, заводятся в `program_document`
   с пометкой «требуется экстракция», видны на `/coverage/sources`.
3. **Документы условий** → `program_document` (sourceUrl/fileUrl/sha, редакция, `effective_from`);
   чек-лист источника (13 пунктов: юрлицо в титуле! редакция по реестру!) —
   `guides/coverage-extraction-prompt.md`. Экстракция правил — агент по промптам A–E × Ф1–Ф7 (D23).
4. **Типы программ.** После экстракции программы видны на карточке СК (вкладка «Распознавание
   и программы»). Строки программ из писем → `program_alias` (kind: program|service|other,
   note = причина, если документа нет).
5. **Разбор писем: парсер или LLM — дерево решения:**
   - видна **чёткая структура** (label→value бланк, таблица, экспорт из системы СК,
     повторяющийся шаблон) → **детерминированный парсер** в `rules_gp.py`
     (ключ = короткое имя СК из `INSURERS` в `extract_dataset.py`);
   - **произвольный текст** или **скан-картинка** → **LLM** (текст/vision через RU-прокси);
   - смешанный бланк (метки + свободный кусок со стабильными ГРАНИЦАМИ — как Альфа) → парсер
     с вырезкой по границам; LLM остаётся фолбэком пропусков.
   Порядок в бою: сначала правила (`apply_rules`), LLM дозаполняет пустое.
6. **Типизация — обязательна** (иначе бардак и баги «в документе одно, парсер находит другое»):
   каждый формат письма → запись в `insurance_company.rules.parsing`
   `[{doc: "ГП — RTF (бланк «Г/П №»)", how: "парсер alfa_gp"}, …]` — видно на карточке СК.
   Образец формата → `doc_template` (тип документа + gold_json эталон; дрейф ловит `parse_log`).
7. **Валидация парсера ДО боя** (ADR D21): регресс по золотому корпусу — правило против
   прод-значений; расхождение = вопрос семантики (пример Альфы: «Срок действия полиса» в бланке
   = срок ГАРАНТИИ; печатная дата сильнее вычисленной). Синк изменённых раннер-файлов
   в локальный `.mail-intake/`.
8. **Проверки после запуска:** `audit_sources.py` (плотность правил — ловит заглушки),
   `verify_rules.py <префикс-документа>`, аномалия-детекты (напр. «detach с заполненным
   сроком действия» = 0, D31).

## B. Новая КЛИНИКА

1. **Ящики.** Почтовые ящики клиники (только чтение! ABSOLUTE) → креды в `.env.local` раннера
   (`MAILBOX_*`) + `_secrets/ACCESS.md`. IMAP SELECT readonly.
2. **Организация.** `organization` создаётся по имени при ingest (`CORPUS_ORG_NAME`);
   письма и реестр несут `organization_id` (мультитенант-скоуп, RBAC по membership).
   ⚠ Известное ограничение: раннер сейчас однокли́ничный (один `CORPUS_ORG_NAME` на прогон) —
   для второй клиники нужен второй профиль раннера (ящики → orgName): час работы, план при появлении.
3. **Страховые и правила покрытия — ПЕРЕИСПОЛЬЗУЮТСЯ**: `insurance_company`, `program_document`,
   `coverage_rule`, `program_alias` — глобальные (без organization_id). Новая клиника получает
   всю базу правил бесплатно; докупаются только корп-программы её договоров (doc_kind='program',
   source='clinic').
4. **Пациенты/карточки** считаются из её писем автоматически (patient_key, computePatientState).
5. **Смоук после запуска:** письма попали → домены определились → неизвестные домены разобраны
   (п. A1) → `/coverage/sources` показывает покрытие клиники → карточка пациента отвечает.

## Аномалия-детекты (прогонять после изменений разбора)
- `detach` с заполненным `valid_until` = 0 (ГП, прочитанное как открепление, D31);
- плотность правил на страницу (`audit_sources.py`);
- Д2/Д3 (ГП без срока/объёма) не растут после изменений парсеров;
- строки программ без алиаса = 0 (запрос в `program_alias` по нормализованным services).
