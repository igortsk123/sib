# План: конвейер покрытия (источники → срезы → ответ ИИ)

> Идея владельца (2026-07-25): DWH-цикл как под OLAP — источник обновился → срез перезалили →
> ИИ (mini-модель) получает при вопросе готовый компакт-контекст. Вопрос-эталон:
> «можно ли удалить 7 зуб за 15000?» → ДА / НЕТ / ПО СОГЛАСОВАНИЮ / писать гарантийник.

## Слои (все локально, всё версионировано)

**L0 — ИСТОЧНИКИ (есть частично):**
- `program_document` ✅ (14 актив., поллер Пн 06:30, цепочки редакций, applies_to/effective_from).
  ДОДЕЛАТЬ: HTML-источники снапшотить в файл (сейчас 3 без файла — качать текст страницы, sha-версионировать
  как PDF); ВСЁ хранится локально в `/opt/sib-storage/programs/` — извлечению нужен файл.
- **Документы клиники** (приложения к договорам, памятки, ПРЕЙСКУРАНТ) — владелец добавит:
  `doc_kind='memo'|'pricelist'`, `source='clinic'`, тот же version-механизм. Не панацея, но точные перечни.
- **Наш реестр** — прецеденты (9 300+ записей: услуги/условия/исходы по программам).

**L1 — STAGING (извлечение текста):** таблица `document_text` (doc_id, version→sha, page, text).
pdftotext (+vision для сканов). Перезаливается при новой версии документа (только затронутый doc).

**L2 — MART (срезы под ИИ):**
- `coverage_rule`: {insurer, program(null=вся СК), service_class, service_pattern («удаление зуб»),
  verdict: covered|excluded|needs_approval|conditional, condition («только после травмы»),
  limit_amount, source_doc+clause («п.3.2.7»), effective_from, applies_to} —
  **генерируется LLM-экстрактором** (сильная модель, батч при обновлении источника) + ручные правки.
  Смена редакции → правила старой версии остаются с периодом применимости (полис живёт по своей редакции!),
  новые — от новой. Проверено на данных: СОГАЗ 3.2.7 даёт ровно «удаление зубов (простое, сложное) покрыто».
- `precedent_mart` из guarantee_letter: {insurer, program, услуга-норм., исход, n, последняя дата} —
  пересборка при ingest/ежедневно. Уникальное преимущество — «эта СК по этой программе удаления одобряла N раз».

**L3 — SERVE (ответ на вопрос из карточки/QR):**
0. ДЕТЕРМИНИРОВАННЫЕ ГЕЙТЫ без LLM (≈50% ответов): откреплён → НЕТ; срок ГП истёк → нужен новый ГП;
   лимит < суммы → НЕТ/частично; дубль/аннулировано → соотв.
1. Ретрив: coverage_rule по (СК, программа, service-match) **редакции на дату полиса** + прецеденты +
   короткие цитаты пунктов из document_text + ГП/лимиты пациента из реестра.
2. LLM (mini): компакт-контекст → вердикт ДА/НЕТ/ПО СОГЛАСОВАНИЮ + пункт-обоснование; при «нужен ГП» —
   **черновик письма-запроса** в страховую (пациент/полис/услуга/обоснование, шаблон per-СК).
3. Обратная связь: ответ страховой → новый прецедент в март (self-learning, закрывает дыры базы).

## Цикл обновления (его «OLAP-перезаливка»)
поллер (неделя) → новая версия源 → L1 re-extract (этот doc) → L2 re-slice (правила этого doc) →
карточки/ассистент автоматически на актуальном. Ручная загрузка от клиники — тот же путь.

## Фазы
- **Ф1 (фундамент):** html-снапшоты в поллере; `document_text` + извлечение; LLM-экстрактор coverage_rule
  для СОГАЗ+Ингосстрах (самые массовые, тексты программ есть); карточка показывает ВЫЖИМКУ правил вместо
  голой ссылки. ~2-3 дня.
- **Ф2 (ответчик):** precedent_mart; детерм-гейты; endpoint «Спросить ИИ» в карточке (вопрос свободным
  текстом → пайплайн L3); лимиты/цены при наличии прейскуранта. ~2-3 дня.
- **Ф3 (генератор ГП + QR):** черновик письма-запроса per-СК; QR-вход пациента (идентификация+согласие,
  152-ФЗ) → тот же L3. Оценка после Ф2.

## Ответы владельца (2026-07-25)
1. Прейскурант НЕ нужен: врач сам пишет сумму и услугу в чате («удалить 7 зуб за 15000») — гейт
   «лимит vs сумма» работает от суммы вопроса + лимитов ГП/программы.
2. Файлы клиники пришлёт позже — не блокирует.
3. **Форма запроса ГП — разведано по Sent (dms@, 128 писем): клиника отвечает REPLY-IN-THREAD на письмо
   страховой** (темы «Re: Томская область, КЛИНИКА…», полис в теме у РГС); портальных форм нет →
   генератор Ф3 = ответ в цепочку. Прочитать 2-3 тела для шаблона — при Ф3.
4. Модель mini — ок.
